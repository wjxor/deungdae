## 팀에서 정해야 할 것 (미결정 — 임의로 구현하지 말 것)

항목마다 지금 값(있는 곳) / 선택지·의견 / 기다리는 것·시한 / 바꾸면 따라오는 일을 적는다. 임시값은 팀이 정하기 전까지 바꾸지 않는다.
안전점수는 요청마다 DB로 다시 센다(`route_cache`는 카카오 경로만 저장). 점수 값을 바꾸면 다음 검색부터 반영되고 시연 경로 점수도 달라질 수 있다.

- **시설 가중치와 가로등·보안등 상한** — 팀 회의, 12주차 1차 배포 전 (10주차 발표 10·11장)
  - 지금: 가로등·보안등 1, CCTV 3, 안심벨 5, 지구대 10 (DB `facility_types.weight`, 마이그레이션 `init`), 구간당 개수 상한 없음. 가로등·CCTV·안심벨은 3주차 발표자료 초안, 보안등·지구대는 2026-10-21 MVP 임시값. 어느 값도 실험으로 정하지 않았다
  - 교수님 코멘트 (2026-10-30 9주차 발표): 이 값을 정한 이유와 60쌍 실험으로 정했는지 물으셔서 임의로 정했다고 답함(상협). 60쌍은 가중치를 고정한 채 정규화와 아래 고르는 기준만 정했다. 또 "60쌍은 너무 적다, 최소 100쌍 이상은 해야 의미 있는 데이터" — 7주차에도 9월 10쌍 실험에 같은 지적이 있었다 (노션 7주차 코멘트)
  - 200쌍 실험 (2026-10-31 PR #49, `docs/safety-score-experiment.md` "200쌍으로 늘림" 4번): 같은 경로 600개로 후보를 비교했다. CCTV 5·안심벨 10·지구대 20으로 올려도 고르는 길이 바뀌는 쌍은 3쌍이다(그런 시설이 있는 구간 자체가 적어서). 가로등·보안등은 여전히 점수의 88.6%(지점으로 세는 지금 서버로는 90.6%)
    - 가로등·보안등을 합쳐 구간당 3개까지 세면 19쌍이 바뀌지만, 초록 구간이 37.9% → 8.8%로 줄어 정규화(원점수 10에서 100점)도 같이 바꿔야 한다
    - 5개까지 세면 색 분포는 그대로이고 8쌍이 바뀐다. 다른 길을 고르는 쌍은 32 → 26쌍
    - 위 쌍 수는 우회 20%·대수로 셀 때다. 지금 서버(지점·우회 30%)로 다시 세면 3개까지 21쌍·5개까지 9쌍이 바뀌고, 다른 길을 고르는 쌍은 36 → 15쌍·29쌍. 드문 시설 상향은 3쌍 그대로 (2026-11-05, `docs/safety-score-experiment.md` "팀 회의에서 볼 것")

- **iOS·Android 배포는 PWA 웹앱으로 해도 되고, AI 기능은 꼭 넣지 않아도 된다** — 교수님 확인 (2026-10-29 상협 전달)

### 안심경로 계산 방식 (FR-006) — B 기본 + A 보강 확정

2026-10-18 상협 확인. 4~7주차 발표자료(승민 작성) 4장의 "B를 기본으로 하고 A로 보강, 추후 시간이 남으면 자체 엔진"과 같다. 아래 표는 결정 당시 비교 자료다.

| 안 | 방식 | 장점 | 약점 |
|---|---|---|---|
| A 경유지 우회 | 안전시설 밀집 지점을 경유지(최대 5개)로 넣어 카카오 경로를 끌어당김 | 카카오 기본 옵션에 없는 새 길을 만들 수 있음 | 경유지 선정 로직을 직접 설계해야 함. 잘못 잡으면 이상한 우회 경로 |
| B 후보 비교 | `route_mode` 3종으로 후보 3개 → 구간별 안전점수 → 최고 점수 선택 | 단순, 예측 가능, 카카오 경로라 안전 | 세 후보가 거의 같으면 고를 게 없음 (가까운 거리일수록 가능성 큼) |
| C 자체 엔진 | OSM 보행자 도로망 + 안전점수 가중치 다익스트라/A* | 정공법, 등대 취지에 가장 가까움 | 도로망 데이터·알고리즘·응답 속도 전부 직접 해결 |

- **지금 구현 (PR #30)**: B의 후보는 최단·넓은 길 우선 2개. 편안한 길은 넣어도 고르는 결과가 같아 뺐다 (`docs/safety-score-experiment.md`)
- **B 기본 + A 보강**: 후보를 구간별 안전점수로 비교하고, 후보가 서로 비슷하거나 최고 점수도 낮으면 경유지를 넣은 후보를 더한다. 조건·개수는 "팀에서 정해야 할 것"
- **9주차 MVP는 B만** — A 보강(경유지 후보 추가)은 MVP 뒤에 붙인다 (2026-10-21 상협)
- **11/06 10주차 발표에는 A 보강 실험 결과(PR #51)만 보여 줬다** — 서버에는 12주차 배포 뒤 조건("팀에서 정해야 할 것")을 정하고 붙인다 (2026-11-04 상협, PR #51 리뷰). 발표까지 남은 날이 하루였고, 경유지 경로는 최단·큰길을 받은 뒤에야 불러서 검색당 카카오가 2 → 최대 4건이며 NFR-001(3초)을 아직 재지 않았다
- **안심경로 우회 한도 30%** — 최단경로보다 30% 넘게 돌아가는 후보는 안심경로로 고르지 않는다 (2026-11-04 승민 제안·상협 동의, PR #51). 20%에서 늘려 200쌍에서 다른 길이 32 → 36쌍(16% → 18%), 늘어난 길도 우회 최대 +23.5%. 시연 경로(카이스트 정문 65 → 75 · +103m, 궁동로데오거리 같은 경로)는 그대로. 최소 점수 차 5점은 아직 임시값
- **C는 9주차 MVP 뒤 여유가 있으면 시도** — 조원이 노션에 조사해 둔 다익스트라·A* 자료를 이때 쓴다
  - 참고 사례 (조원 조사): safe-routes-to-school, Risk-Aware-Pedestrian-Navigation-System, SafePath — 전부 자체 도로망 + 가중치 다익스트라/A*(C안 계열). C안 시도 시 구조 참고
- 근거: `route_mode` 비교 실험 (2026-09-29, `docs/route-mode-experiment.md`) — 10쌍 중 3쌍은 후보가 사실상 하나, 실질 후보는 2개

## 교수님께 확인할 것

지금은 없다. PWA 웹앱 배포와 AI 기능이 필수가 아닌 것은 확인했다 ("결정된 것").

## 발표 대비 답변

- **왜 카카오인가**: "결정된 것"의 카카오 근거 그대로. 경로 호출은 모듈로 분리해 필요하면 티맵으로 교체 가능
- **카카오 "편안한 길"과 뭐가 다른가**: 편안한 길은 경사·계단 기준, 등대는 야간 안전시설 밀도 기준
- **수익 모델**: 시민 앱은 무료, 누적 안전점수·제보 데이터를 지자체의 가로등·CCTV 설치 우선순위 근거로 제공
- **가중치는 어떻게 정했나** (9주차에 받은 질문): 3주차 초안에 보안등·지구대 MVP 임시값을 더한 것이고 실험으로 정하지 않았다. 60쌍 실험은 정규화와 안심경로를 고르는 기준을 정했다. 그 뒤 200쌍으로 늘려 후보를 비교하니, CCTV·안심벨·지구대 가중치를 두 배로 올려도 고르는 길은 200쌍 중 3쌍만 바뀌고, 결과를 바꾸는 것은 가로등·보안등을 구간당 몇 개까지 셀지(상한)였다. 그래서 가중치는 구글폼 설문으로 시설별 중요도를 받아 상한과 함께 12주차 배포 전에 정한다 (10주차 발표, "팀에서 정해야 할 것")
- **AI 요소는?**: 교수님께 필수가 아니라고 확인했다. 붙인다면 제보 텍스트 분류나 구간 위험도 예측 정도의 자리가 있다
- **위험하면 자동으로 알람·신고는?**: 112 자동 신고는 공개 API가 없어 앱으로도 안 된다(서울 "안심이"도 관제사가 CCTV로 확인한 뒤 출동). PWA로는 SOS 버튼과 도착 확인 타이머까지, 앱이면 화면이 꺼져도 감지할 수 있다 ("팀에서 정해야 할 것"의 SOS 항목)
