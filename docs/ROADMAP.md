## 팀에서 정해야 할 것 (미결정 — 임의로 구현하지 말 것)

항목마다 지금 값(있는 곳) / 선택지·의견 / 기다리는 것·시한 / 바꾸면 따라오는 일을 적는다. 임시값은 팀이 정하기 전까지 바꾸지 않는다.
안전점수는 요청마다 DB로 다시 센다(`route_cache`는 카카오 경로만 저장). 점수 값을 바꾸면 다음 검색부터 반영되고 시연 경로 점수도 달라질 수 있다.

## 결정된 것

결정마다 한 줄로 적는다. 결정할 때의 세부와 근거 원문은 `docs/HISTORY.md` 맨 끝 "옛 ROADMAP 원문".

- **스택**: TypeScript + React(Vite, PWA) / TypeScript + NestJS / PostgreSQL + PostGIS(Supabase) / Python 전처리 — 3주차 발표자료 14페이지
- **개발 환경**: 로컬 개발, 도커는 당분간 안 씀. DB는 Supabase 공용 인스턴스를 셋이 같이 사용
- **저장소**: 상협 개인 계정의 공개 저장소 `wjxor/deungdae`, 모노레포 — `shared/types.ts`를 같이 import하고, 3명 팀이라 나누면 관리만 늘어서. 라이선스는 MIT (2026-10-29 상협, PR #43)
- **대상 지역(NFR-002)**: 대전광역시 전체 — 2026-10-02 팀 확정. 시설 데이터가 5개 구 모두에 있고, B안은 경로 주변만 조회해 넓어도 느려지지 않음
  - 유의: 구별 밀도 차이가 큼(가로등은 유성구에 40%, 비상벨은 서구가 적음) → 구끼리 점수를 비교할 때 데이터 편차를 고려
- **지도·경로 API는 카카오**, 티맵 보행자 API는 예비 — 카카오 도보 경로 품질 문제 시 경로 호출 모듈만 교체
  - 근거: 공식 문서로 비교해 도보 경로 기능(경유지 5개, 탐색 옵션)·무료 한도(일 1,000건)가 같고, 티맵의 구간별 도로·시설 정보는 점수에 쓰지 않아서. 키도 이미 있었음
- **카카오 앱은 상협 계정의 "등대" 하나** — JS 키·REST 키 모두 이 앱 (2026-10-14 PR #10, 승민 동의). 콘솔 설정은 `docs/EXTERNAL_APIS.md`
- **안전점수**: 공공데이터 시설 밀도(가로등·보안등·CCTV·안심벨·지구대)만 사용. 지하보도·육교·계단 같은 구간 성격은 반영하지 않음
- **24시 시설(편의점·심야 약국) 제외** — 2026-10-10 승민 제안·상협 동의 (PR #6). 24시간 운영인지 알 수 없어서 (REQUIREMENTS FR-002)
- **안전시설 아이콘(FR-002)**: CCTV·안심벨·지구대만 표시, 가로등·보안등은 점수에만 — 2026-10-14 승민 제안·상협 동의 (PR #9). 합쳐 7만 개가 넘어서
  - 경로 화면(S3)에서도 안심벨·지구대는 늘 표시하고 CCTV는 숨긴다 — 2026-10-29 상협 제안·승민 (PR #45). 출발지 입력(S2)은 모두 숨김
- **주야간 판별(FR-005)**: 일출·일몰 자동 판별 + 수동 전환. 한국천문연구원 출몰시각 API를 서버에서 하루 1회 호출·캐싱
- **제보(FR-009·010)·회원·로그인(FR-011)은 Could** — 13주차 여유 시. 로그인 필요 여부·사진 첨부는 "팀에서 정해야 할 것"

### 안심경로 계산 방식 (FR-006) — B 기본 + A 보강 확정

2026-10-18 상협 확인. 4~7주차 발표자료(승민 작성) 4장의 "B를 기본으로 하고 A로 보강, 추후 시간이 남으면 자체 엔진"과 같다. 아래 표는 결정 당시 비교 자료다.

| 안 | 방식 | 장점 | 약점 |
|---|---|---|---|
| A 경유지 우회 | 안전시설 밀집 지점을 경유지(최대 5개)로 넣어 카카오 경로를 끌어당김 | 카카오 기본 옵션에 없는 새 길을 만들 수 있음 | 경유지 선정 로직을 직접 설계해야 함. 잘못 잡으면 이상한 우회 경로 |
| B 후보 비교 | `route_mode` 3종으로 후보 3개 → 구간별 안전점수 → 최고 점수 선택 | 단순, 예측 가능, 카카오 경로라 안전 | 세 후보가 거의 같으면 고를 게 없음 (가까운 거리일수록 가능성 큼) |
| C 자체 엔진 | OSM 보행자 도로망 + 안전점수 가중치 다익스트라/A* | 정공법, 등대 취지에 가장 가까움 | 도로망 데이터·알고리즘·응답 속도 전부 직접 해결 |

- **지금 구현 (PR #30)**: B의 후보는 최단·넓은 길 우선 2개. 편안한 길은 넣어도 고르는 결과가 같아 뺐다 (`docs/safety-score-experiment.md`)
- **B 기본 + A 보강**: 후보를 구간별 안전점수로 비교하고, 후보가 서로 비슷하거나 최고 점수도 낮으면 경유지를 넣은 후보를 더한다. 조건·개수는 "팀에서 정해야 할 것"
- **9주차 MVP는 B만** — A 보강(경유지 후보 추가)은 MVP 뒤에 붙인다 (2026-10-21 상협)
- **C는 9주차 MVP 뒤 여유가 있으면 시도** — 조원이 노션에 조사해 둔 다익스트라·A* 자료를 이때 쓴다
  - 참고 사례 (조원 조사): safe-routes-to-school, Risk-Aware-Pedestrian-Navigation-System, SafePath — 전부 자체 도로망 + 가중치 다익스트라/A*(C안 계열). C안 시도 시 구조 참고
- 근거: `route_mode` 비교 실험 (2026-09-29, `docs/route-mode-experiment.md`) — 10쌍 중 3쌍은 후보가 사실상 하나, 실질 후보는 2개

## 주차별 일정 (매주 금요일 수업, 15주)

주차는 학사 달력 기준 — 2026-10-02 수업이 5주차. 4주차(추석)·6주차(한글날)가 휴강이라 노션은 4-5주차로 묶고, 6주차 없이 7주차부터 한 주씩 둔다. 휴강분은 학기 말에 보강하고, 15주차 보강일에 최종 발표. 표에는 날짜를 적지 않는다.

| 3 | 요구사항·화면 설계 | FR/NFR 정의, 와이어프레임, MoSCoW, 3주차 진행보고 | 완료 |

## 교수님께 확인할 것

지금은 없다. PWA 웹앱 배포와 AI 기능이 필수가 아닌 것은 확인했다 ("결정된 것").

## 발표 대비 답변

- **왜 카카오인가**: "결정된 것"의 카카오 근거 그대로. 경로 호출은 모듈로 분리해 필요하면 티맵으로 교체 가능
- **카카오 "편안한 길"과 뭐가 다른가**: 편안한 길은 경사·계단 기준, 등대는 야간 안전시설 밀도 기준
- **수익 모델**: 시민 앱은 무료, 누적 안전점수·제보 데이터를 지자체의 가로등·CCTV 설치 우선순위 근거로 제공
- **AI 요소는?**: 교수님께 필수가 아니라고 확인했다. 붙인다면 제보 텍스트 분류나 구간 위험도 예측 정도의 자리가 있다
- **위험하면 자동으로 알람·신고는?**: 112 자동 신고는 공개 API가 없어 앱으로도 안 된다(서울 "안심이"도 관제사가 CCTV로 확인한 뒤 출동). PWA로는 SOS 버튼과 도착 확인 타이머까지, 앱이면 화면이 꺼져도 감지할 수 있다 ("팀에서 정해야 할 것"의 SOS 항목)
